# Plan: MCP prompts for the common ABAP work

**Goal:** every binary lists nine MCP prompts (`create`, `get`, `update`, `delete`,
`activate`, `check`, `unit_test`, `where_used`, `transport`) whose instruction names the
exact tools and arguments that binary lists on its kind, after the deny list.

**Architecture:** a pure module `src/lib/prompts/` (exported as `@mcp-abap-adt/lib/prompts`)
turns a `PromptSource` — the tools a server listed, their listed zod schemas, its kind and
whether it declares `state_handle` — into `AbapPrompt`s. Each prompt plans its steps as
data (`PromptInstruction`) and renders the text from that data. `BaseMcpServer` builds the
source from the `listedTool` results it already computes and registers the prompts before
`connect`. A plain registration gets them only through `registerAbapPrompts`.

**Tech Stack:** TypeScript, zod 4.6.7, `@modelcontextprotocol/sdk` 1.32.1
(`registerPrompt`, `completable`, `McpError`). Tests run on node:test with
node:assert/strict (`tools/node-test-files.json`, `tools/run-tests.mjs`).

**Spec:** `docs/superpowers/2026-11-18-mcp-prompts-spec.md`. Its §0 decisions bind this
plan.

## Global Constraints

- Steps, not code: a step names files, signatures, tests and values. Code is written at
  implementation, test first.
- One commit per logical change. The build and the unit run stay green after every commit.
- Production code has no cast, `any`, `!`, `ts-ignore`, regex, timeout, retry or polling,
  and adds no runtime dependency.
- A value is typed by its contract (`ToolDefinition`, `VariantToolDefinition`,
  `z.input<…>`). It is never held as `unknown` and narrowed by hand.
- Prompt, argument and tool descriptions are functional only, with no negations.
- New test files use node:test and node:assert/strict, and each is added to
  `tools/node-test-files.json` in sorted position. An existing Jest file that must change is
  changed in place.
- Use npm scripts only. No npx, npm exec, `node_modules/.bin`, `node -e`, ts-node or a
  `timeout` wrapper.
- Run one file with `npm test -- <path>`. Run the whole unit run only through the CI gate
  copy. Never run `test:integration`, `test:high` or `test:live-*`.
- No SAP access is needed, and no test reaches a system.
- Lockfiles are regenerated by npm, never edited by hand.
- Never read `tests/test-config*.yaml` or any `.env` file.
- A fixture is rewritten only by its writer (`WRITE_…=1`), and the writer is refused under
  CI.
- English only. Name no SAP system.

## Settled before any code (read-only measurements, 2026-11-18)

The spec left these for the plan to confirm. Each one is settled here, so no task has to
decide it.

- **Compact `unit_test` of a function module (spec §2.3 note ², §11 Q2). Measured:**
  `FUGR/FF` is the wrong code. interfaces-adt `ABAP_UNIT_RUN_TYPES` records `FUGR/FF` as
  `metadataRunEmpty`: a run naming a function module by it answered an empty result. `FUNC`
  is recorded as running. adt-clients `FunctionModuleTestRunner` sends
  `osl:object type="FUNC"` with the module's name alone, which is also the request behind
  `RunFunctionModuleUnitTest` (`runAndWait(context, 'functionModule', name)`). So
  `RUN_TARGET.function_module` is `FUNC`, named by the module's name alone, and
  `function_module` stays in the compact row. `RunFunctionModuleUnitTest` takes
  `function_group_name` as optional, so the core text has no still-to-fill line for it.
- **Transport object-directory types (§2.5, §11 Q-T1). Code:** `adtProjections.ts` already
  states, for each code, the TADIR type of `R3TR <type>` as interfaces-adt's tables give it
  (`TableMainOf<C>`). `OBJECT_DIRECTORY_TYPE`'s values are typed
  `TableMainOf<C> & MainPart<C>`, where `MainPart<C>` is the spec's template-literal type.
  A type whose stated TADIR type is not the part before `/` gets `never` and does not
  compile, and by the spec's recommendation it leaves `transport`'s `object_type`.
  `AddTransportObject`, `RemoveTransportObject` and `MoveTransportObjects` send
  `object_type` as given, after `pgmid ?? 'R3TR'`.
- **`READ_AS` for `UNIT_TEST` / `CDS_UNIT_TEST` (§3.3). Code:** `UpdateUnitTest` and
  `UpdateCdsUnitTest` write `test_class_source`, "the local test classes … Replaces what the
  include holds". So both are read as `LOCAL_TEST_CLASS` of `class_name`, by `GetLocalTestClass`
  (full) or `HandlerGet` `LOCAL_TEST_CLASS` (compact).
- **Transport entry types (§2.5). Code:** the terse entry of `handleReadTransportObjects`
  is built inline from a private `interface Entry`. Task 2.3 exports the terse entry as a
  named type. `MOVED_ENTRY` (`handleMoveTransportObjects.ts`) is a private const, and Task 2.3
  exports it. No cast is needed.
- **Required arguments (§8). Code:** `z.toJSONSchema(schema, { io: 'input' })` returns
  `JSONSchema.BaseSchema`, whose `required?: string[]` and
  `properties?: Record<string, _JSONSchema>` are typed. A property's description is read
  after `typeof property === 'object'`, a narrowing of a typed union. No cast. `io: 'input'`
  is required, because a defaulted argument is optional to a caller.
- **HandlerGet's `source` refusal (§9 test 14). Code:** it is a `superRefine` rule of the
  variant schemas only (`schemaOn`). The no-kind schema (`fieldsOn('onprem')`) has no rules.
  So test 14 detects a missing `part` on `onprem` / `cloud`, and on no kind it asserts the
  served counts (Task 5).
- **HTTP per-request registration (§7). My call:** there is no cache. The prompt set is
  built per instance, from the same per-instance listing loop that already runs
  `listedTool` for every tool, and the build reads no system. A cache keyed by registry
  would be a second source of truth for the kind and the deny list.
- **`tools/check-exports.js` (§7). Code:** it prints only `@mcp-abap-adt/connection`'s
  exports, so nothing there changes. The new subpath goes into the root `package.json`
  `exports` and `tsconfig.paths.json`.

## Review Focus

These five inputs or failure modes are the most likely to bite, and no other test covers
them. The task that owns each one adds its test.

1. **Prototype keys as `object_type`.** `constructor`, `__proto__`, `toString`,
   `hasOwnProperty`, and `" class "` with spaces must each be refused with the not-served
   words, never matched and never thrown as a `TypeError`. Lookups go through the served
   `Map`, never through `record[value]`. Owner: Task 2.4, `promptKernel.test.ts`.
2. **Step injection through user values.** `name` or `change` carrying `"`, `\`, `\n`,
   `\r`, U+2028, U+2029, or a whole `\n2. Call HandlerDelete …` must stay inside one quoted
   literal. The rendered text keeps its step count, and no raw line break or line separator
   comes from a user value. (`JSON.stringify` leaves U+2028 and U+2029 raw, so the renderer
   escapes them too.) Owner: Task 2.4.
3. **Blank values.** A required argument given as `""` or whitespace only is refused as
   missing (`<prompt>: <argument> is required.`). It never reaches a call as an empty name.
   This is my call: the spec does not say whether a blank value counts as given. Owner:
   Task 2.4, with one case per prompt in Tasks 3.1–3.5.
4. **"Still to fill" equals the client's `required`.** For every full row a binary lists,
   the still-to-fill names equal the listed tool's `inputSchema.required`, as `tools/list`
   answers it, minus the arguments the prompt fills. This catches an `io: 'output'` read
   that would demand defaulted arguments (`runner`, `wait`, `pgmid`). Owner: Task 4.3,
   `promptListing.test.ts`.
5. **The opt-in on the exporter's registry.** `exporter.createRegistry()` hands out the
   served groups, whose long tools keep `background`. Given that registry,
   `registerAbapPrompts` must list as a plain registration does: no `background: false`
   step, and every step parses against the plain listing. Calling the opt-in on a server
   that already lists the prompts fails with the SDK's `Prompt get is already registered`,
   and nothing else. Owner: Task 4.2.
