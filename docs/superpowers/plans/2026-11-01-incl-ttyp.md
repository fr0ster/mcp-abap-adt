# Plan: the server writes program includes and table types (#336)

Bound by the goal `docs/superpowers/2026-11-01-incl-ttyp-goal.md` and the spec
`docs/superpowers/specs/2026-11-01-incl-ttyp-design.md` (owner-approved; its §9 decisions
Q1–Q8 override the rest of it). Precedence: the owner's rules > goal > spec > plan. Where the
spec disagrees with itself or with the code, the section below says how, and the plan follows
the correction. The spec is not edited.

Every step is TDD: the failing test first, run and seen red, then the code, then green. A step
that guards a rule also proves the rule is load-bearing: break it on purpose, watch its test go
red, restore. A step is done when its gate is green and its commit is made. No time estimates.

## Spec corrections

Each was found by reading the spec against itself, §9, and the code in this worktree
(adt-clients 39.0.0, interfaces-adt 24.0.1).

1. **§3.2 `UpdateTableType` row** says "lock → write → unlock → activate if asked". §4.2 (Q7)
   and `UpdateDomain` (Code `src/handlers/domain/high/handleUpdateDomain.ts:179-267`) say:
   lock → read → patch → PUT → check → unlock → long-poll read → activate, with `activate`
   default **true** (`activate !== false`). The `CreateTableType` row gets its chain too (item 2).
2. **§4.2 `CreateTableType` chain** omits two steps `CreateDomain` runs
   (`handleCreateDomain.ts:191-310`): the name `validate` before the create, and the long-polling
   `readMetadata` wait between the unlock and the check. The plan copies the domain whole:
   validate → create → LOCK → read → patch + PUT under the lock → UNLOCK (every path) → wait →
   check → activate (default true).
3. **§4.2 `UpdateTableType` order**: `UpdateDomain` runs the check *inside* the lock (lock →
   read → PUT → check → unlock), then the wait, then the activation. The spec's "UNLOCK → check"
   is not the domain's order; the plan follows the domain.
4. **§4.2 "as `CreateDomain`" must not bring its defaults.** `CreateDomain` declares schema
   defaults (`datatype` `CHAR`, `length` 100, `decimals` 0) and fills them in code
   (`|| 'CHAR'`); the MCP SDK fills a declared schema default into the arguments (CHANGELOG
   22.0.1). §4.2's rule "a property not given leaves SAP's value" holds only if no definition
   property declares a schema default and none is filled in code. Only `activate` declares
   `default: true`.
5. **§4.2 `UpdateTableType` parameters**: `UpdateDomain` requires `package_name`, which feeds
   only `validateTransportRequest`, a no-op (Code `src/utils/transportValidation.ts:10-18`). The
   spec omits it; the plan follows the spec (no `package_name` on `UpdateTableType`).
6. **§8.1 "`UpdateTableType` sends exactly LOCK, PUT, UNLOCK (no GET)"** contradicts §4.2. Its
   wire is LOCK, GET (metadata), PUT (the patched document), POST check, UNLOCK, GET
   (long-poll), POST activation when `activate`. "The document byte for byte as given" holds for
   `UpdateIncludeMetadata`, `HandlerUpdate TABLE_TYPE` and `HandlerUpdate INCLUDE part:
   'metadata'`, not for `UpdateTableType`, whose PUT is the patched read.
7. **§8.2 table-type live sequence** starts "create → `GetTableType` → `UpdateTableType` with a
   row type". After Q7, the definition comes with `CreateTableType` (activated by default);
   `UpdateTableType` then changes one property. The Q7 value measurement (step 6) is a run of its
   own before the schema names the values.
8. **§5 has no `HandlerWhereUsed TABLE_TYPE`** (Q6). `COMPACT_WHERE_USED_ROUTES` is
   `satisfies Record<string, TypeName>` and `CompactWhereUsedName<P>` looks each route up in
   `TYPE_NAMES` (Code `src/lib/adtProjections.ts:449-470`), which has no name for `TTYP/DA`. Q6
   (route by the code, no new name) needs both types widened to take a where-used code beside a
   name; `TABLE_TYPE` joins both lists of `COMPACT_WHERE_USED`.
9. **§6 `IAdtTransportAware` "only if Q4 adds a transport read"**: Q4 decided no. It is dropped
   from `DdicTableTypeApi`; `readTransport` stays unreachable through the contract.
10. **§7 CHANGELOG `### Added`** misses `HandlerWhereUsed`'s `TABLE_TYPE` (Q6) and the
    definition properties of `CreateTableType` / `UpdateTableType` (Q7).
11. **§7 "surface fixtures … additions only"** is not so. `GetInclude` gains `part` and
    `version` (a changed row: an allowed addition in `toolSurface.test.ts`'s ratchet);
    `HandlerUpdate` gains `part` (`compact/tests/fixtures/surface.json`); `CreateProgram`'s
    description and enum change (Q1; the surface fixture holds parameters, the generated tool
    docs hold the enum text). The refreeze is recorded as the ninth deliberate move in
    `toolSurface.test.ts`, as the eight before it are.
12. **§7 tool-search queries** "change a report's include" and "create a table type" do not
    exist in `toolRetrieval.test.ts`; they are added, not re-checked.
13. **§8.1 "with `INCLUDE` in `HandlerGet` and `HandlerDeletionCheck` on cloud only"** reads as
    "only on cloud". Meant: on cloud, `INCLUDE` is offered by `HandlerGet`,
    `HandlerDeletionCheck` and (already) `HandlerWhereUsed`, and by no other compact handler.
14. **§5 `HandlerUpdate` `part` "(`'source'` default)"**: a description default only, no schema
    `default` (item 4's reason) — a filled `part: 'source'` on every call would reach types whose
    `source_code` is a metadata document.
15. **§5 `HandlerActivate`**: unstated what one `INCLUDE` / `TABLE_TYPE` alone does. Q8 leaves
    `SINGLE_ACTIVATION_ROUTES` unchanged, so `COMPACT_SINGLE_ACTIVATION` does not gain them and
    one such object goes to group activation, as `ActivateObjects` sends it today.
16. **§4.1 `GetInclude` metadata read**: `GetProgram` reads metadata through
    `readProgramMetadata` in `src/lib/strategies/metadataReads.ts`; the plan adds
    `readIncludeMetadata` there beside `readTableTypeMetadata`. Neither joins `READS` (the package
    walk's metadata reads): that would change `packageWalk`'s answers, which the spec does not ask.
17. **§1 basis740 note**: `ADT_TYPES_BASIS_740` `PROG/I` lists neither `deletionCheck` nor
    `updateMetadata` (Code `AdtTypeTables.d.ts:979`); §10 names only the first.
18. **Citations that moved**: `COMPACT_CRUD_MATRIX` is in `src/lib/compact/compactMatrix.ts`, not
    `compactObjectTypes.ts`; `compactPartRoutes.ts` is
    `compact-readonly-entries/src/handlers/compactPartRoutes.ts`, its metadata-only list
    `SOURCELESS` at `:181-186`; `handleCreateOnly.ts` / `handleUpdateUnderLock.ts` are in
    `src/handlers/common/low/`; `lockObject`'s program case is `handleLockObject.ts:192-196`
    (`:204-208` is the function module's); `DELETION_TARGETS` is at `deletionTargets.ts:102`, its
    `PROGRAM` entry `:148-157`.
