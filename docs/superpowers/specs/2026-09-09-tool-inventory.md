# Tool inventory — the stage-1 compatibility table

**Status: in progress.** Groups filled so far: **system and search (34)**.
Remaining: readonly (34), compact (22), high (156), low (116).

This is the table the design
(`docs/superpowers/specs/2026-09-08-result-error-strategies-design.md`) makes a
precondition for stage 3: *"No tool loses an input or an output field that is not in
it."* Every later migration plan is written from these rows.

The first five columns — tool, group, implementation files, visible in, current inputs —
are carried **verbatim** from `docs/superpowers/specs/2026-09-09-tool-inventory-rows.md`
(Task 1a, commit `d74a797`), which produced them from two committed scripts and had them
re-derived independently by two reviewers. They are not re-derived here. Where a row of
that document looks wrong, it is recorded under **Findings about the skeleton** below
rather than silently corrected.

The remaining eight columns come from reading each handler body — not its
`TOOL_DEFINITION` — on branch `feat/answer-adapter`, which is `main` plus the two Task 1a
commits. No handler was modified by this task.

## How to read the eight new columns

| column | what is in it |
|---|---|
| current default output | the object the caller receives today, field by field. Where the handler builds a JSON string and hands it to `return_response`, the fields listed are the fields **inside** that string; the MCP envelope is mentioned only where it deviates from `{ isError, content: [{ type: 'text', text }] }` |
| transformation today | how the ADT answer becomes that output — the parser by name, or "returns the document" where the body is passed through untouched |
| error decision today | what the handler treats as a failure: an HTTP status, a thrown error, a field in the document — and what it treats as a **success** that a reader might not expect |
| guarantees | every check, rejection or resolution the handler performs beyond passing the answer through, quoted from its own comment where it has one. A guarantee that depends on a field is a reason that field stays |
| new inputs | the inputs after `detail` is added and any removed parameter is gone. **`+detail`** is shorthand for "every current input unchanged, plus `detail`: `'terse' \| 'full' \| 'raw'`, default `'terse'`" |
| new terse projection | the fields `terse` carries. `full` carries the whole parsed structure and `raw` the document, per the design, so only `terse` needs stating |
| dropped | every field in *current default output* absent from *new terse projection* |
| justification | why each dropped field may go |

**The rule for the last two columns**, from the design: *a field the caller needs to make
the next call — an object name it did not already have, a transport number it must quote —
stays in `terse`; a field that only describes what just happened moves to `full`.*

Two consequences of that rule recur often enough to state once rather than in 362 rows:

- **`success: true` is dropped everywhere it appears.** It is the same claim the MCP
  envelope's `isError: false` already makes, and under the new adapter a value is
  reachable only through `ok` — so a payload asserting its own success is not merely
  redundant, it is the shape the three masking fixes removed.
- **A field that echoes the caller's own argument is dropped.** `class_name` in the answer
  to `GetClass(class_name: 'ZCL_X')` is not a name the caller "did not already have".
  Where an argument is *normalised* before use — uppercased, trimmed, resolved against a
  second object — the normalised value **stays**, because that one the caller did not have.

Where a row says *"returns the document"* in *transformation today*, the current default
output already is the raw body. Moving that tool to a `terse` projection is a **reduction
of the default**, and the row says so: a caller that parses the XML itself must ask for
`detail: 'raw'`.

## Masking: refusals reported as empty successes

This repository has fixed three defects of one shape — read masking, deletion masking,
activation masking — each a refusal delivered as `{ success: true }` with nothing in it.
The **error decision today** column names every further instance found, and they are
collected here as they are found, group by group.

From **system and search**:

| tool | the masking |
|---|---|
| `GetTransaction` | unconditional. The handler is a stub: it ignores `transaction_name`, makes no request, and answers `isError: false` with `{ message: 'Not implemented' }`. Its parser `_parseTransactionXml` is dead code |
| `GetSqlQuery` | `parseSqlQueryXml` catches its own parse failure and returns `{ columns: [], rows: [], error: 'Failed to parse XML response' }`; the handler returns that with `isError: false`. A document it could not read is delivered as an empty result set |
| `GetObjectNodeFromCache` | when expanding `OBJECT_URI` throws, the failure is written **into the returned node** as `object_uri_response: 'ERROR: <message>'` and the node is answered as a success |
| `SearchObject` | a 200 whose body contains no `<adtcore:objectReference ` is answered `{ isError: false, content: [] }` — an empty `content` array with no text at all. "Found nothing" is a legitimate search answer, but the same branch swallows an unparseable or unauthorised 200, and the caller cannot tell them apart |
| `GetObjectsByType` | a 200 the regex could not read yields the text `No objects found for node_id …` with `isError: false` — same conflation as `SearchObject`, in prose rather than an empty array |
| `GetAdtTypes` | a 200 that is not a `nameditem:namedItemList` yields the text `[]` with `isError: false` |
| `DescribeByList` | an object that could not be described is **dropped from the answer** by an empty `catch {}` with no marker, so a short list reads as "these are the objects". Separately, its outer catch answers `{ isError: true, content: [] }` — an error with no message |
| `GetObjectInfo` | enrichment failure is swallowed by `catch (_e) {}`, leaving `OBJECT_DESCRIPTION` and `OBJECT_PACKAGE` `undefined` on every node. Since the enrichment call is itself broken (see Findings), this is the *only* outcome |
| `RuntimeRunClass`, `RuntimeRunProgram` | `output` is `response.data` when it is a string **and the empty string when it is not** — a body the handler did not recognise becomes `output: ''` alongside `success: true` |

## Findings about the handlers

Recorded, not corrected — this task writes one document and touches no `src/`.

### `GetObjectInfo`'s `enrich` has never worked

`enrichNodeWithSearchObject` (`handleGetObjectInfo.ts:82-87`) calls

```ts
const searchResult = await handleSearchObject(context, {
  query: objectName, object_type: objectType, maxResults: 1,
});
```

`handleSearchObject` destructures `object_name` and answers
`return_error('object_name is required')` when it is absent — so every enrichment call
returns `isError: true`, the `!searchResult.isError` gate below it is false, and the loop
never runs. Even if the parameter name were fixed, the body would still fail: the function
feeds `entry.text` to an `XMLParser` and looks for `adtcore:objectReferences`, while
`handleSearchObject` returns **tab-separated text**, not XML. Two independent defects, so
`OBJECT_DESCRIPTION` and `OBJECT_PACKAGE` are always `undefined` and `enrich` costs a
round trip per node for nothing.

This matters to the migration: a plan reading only the `TOOL_DEFINITION` would preserve
`enrich` as a working feature.

### Three inputs are accepted and never read

| tool | input | evidence |
|---|---|---|
| `GetAdtTypes` | `validate_type` | the handler signature is `(context, _args)`; nothing validates a type. The description advertises "or validate a specific type name" |
| `GetPackageTree` | `debug` | declared in the schema with a description promising "diagnostic metadata in response (counts, types, hierarchy info)"; `args.debug` appears nowhere in the body |
| `GetSession` | `force_new` | read into a local and used only to decorate a debug log line; no branch depends on it |

### `GetSession` returns `session_state: null` while 100+ tools ask for it

`handleGetSession.ts:69` hardcodes `session_state: null` with the comment *"Session state
management is now handled by auth-broker"*. Every `*Low` tool's schema still describes
`session_state` as *"Session state from GetSession (cookies, csrf_token, cookie_store).
Required if session_id is provided."* The documented handshake cannot be completed with
what `GetSession` returns.

### `objectsListCache` is written in two incompatible shapes

`GetTypeInfo`, `GetWhereUsed` and `GetObjectsByType` call `objectsListCache.setCache()`
with a whole **MCP result object** (`{ isError, content }`). `GetObjectsList` calls it with
`{ parent_name, parent_tech_name, parent_type, total_objects, objects }`.
`GetObjectNodeFromCache` reads `cache.objects` — which only the second shape has. A cache
last written by any of the first three makes `GetObjectNodeFromCache` answer
`Node not found in cache` regardless of what is in it.

### Content items of type `json`, and results with no `isError`

Six handlers return `content: [{ type: 'json', json: … }]` — a content item type the MCP
content schema does not define: `GetObjectNodeFromCache`, `GetTypeInfo`, `GetWhereUsed`,
`GetObjectInfo`, `GetAbapSystemSymbols`, `GetTransaction`.

Two omit `isError` from the success result entirely: `GetObjectNodeFromCache` and
`GetObjectsList`. `GetObjectsList` additionally returns a top-level `cache` key beside
`content`, which is not part of an MCP result.

### `GetObjectInfo` is a fourth unbounded-ish traversal

The design names three traversals to bound (`GetPackageTree`, `GetPackageContents`,
`GetObjectsList`). `GetObjectInfo` also recurses — `buildTree` calls itself per group node
— but is already bounded by `maxDepth` (default 2 for `PROG/*` and `FUGR/*`, 1 otherwise).
It is not unbounded, so it needs no new bound; it is recorded so the migration does not
discover it as a surprise.
